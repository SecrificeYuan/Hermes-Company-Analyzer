# Hermes Company Analyzer 需求与范围

**状态：已确认，允许进入架构与契约设计**  
**项目背景：** 杭州银行企业赛题「X-Ray｜透视·真相」  
**文档目的：** 在技术选型、架构设计和接口契约前，冻结本次 Hackathon 的产品范围与验收目标。

## 1. 问题与目标

银行在接收企业存款、提供授信或开展初步尽调时，需要从财务报表、公司公告、信用与司法风险、新闻舆情等分散的公开信息中判断企业的经营状况和潜在风险。非金融专业人员很难快速获得一份有证据、可理解的企业全景判断。

Hermes Company Analyzer 是一个基于公开信息的企业分析原型。用户输入一家企业后，系统将来自官方 API、公开网页、合规开放数据和社交平台的分散线索组织成企业全景、财务健康、信用与风险事件、经营与舆情四类结果，并让每个重要判断能够回溯至来源。

本期目标是帮助用户在一次演示中回答三件事：

1. 这家企业当前整体风险处于什么水平。
2. 支撑该结论的关键正面与负面信号分别是什么。
3. 每个信号来自何处、发生在何时，数据是否足够支持判断。

## 2. 目标用户与使用场景

| 角色 | 使用场景 | 希望得到的结果 |
|---|---|---|
| 银行客户经理或初步尽调人员 | 接到企业存款、贷款或合作需求后的快速预筛 | 短时间理解企业是否存在需进一步核验的风险 |
| 企业投资、合作或招聘决策者 | 需要了解一家企业的经营与风险情况 | 获得非专业人士也能理解的企业健康画像 |
| Hackathon 评委 | 演示题目解决方案 | 看到从原始公开线索到可解释结论的完整链路 |

## 3. 本期范围

### 3.1 分析对象

- 仅支持 A 股上市公司，以公司名称或股票代码作为输入。
- 系统必须针对用户给定的企业在线获取真实公开数据；不以预置企业数据代替查询结果。
- 对无法匹配、信息不足或数据源暂不可用的企业，系统应说明具体缺失维度，不输出看似精确的完整评分。
- 现场演示保证网络可用；是否额外准备演示企业由团队稍后决定。

### 3.2 核心用户流程

```text
输入公司名称或股票代码
  → 确认匹配的企业
  → 生成或读取企业分析
  → 查看整体结论与关键风险
  → 下钻财务、信用风险、经营与舆情维度
  → 打开来源，核验原始线索
```

### 3.3 MVP 运行边界

- 使用 Next.js + TypeScript + SQLite 运行在单机环境；不追求高并发、高可用或多实例扩展。
- Route Handler 只创建和读取 SQLite 作业。单个 TypeScript Worker 轮询待处理作业，完成采集、规范化、函数分析和 LLM 叙述。
- SQLite 保存任务状态、短期缓存、快照索引和分析报告；不使用 Redis、BullMQ、消息队列或额外缓存服务。

### 3.4 必须交付的功能（P0）

| 编号 | 功能 | 用户可见行为 | 验收标准 |
|---|---|---|---|
| R-01 | 企业查询 | 用户可用公司名称或股票代码查询 A 股企业 | 对任一可查询的 A 股企业得到唯一匹配结果；无法匹配时显示明确提示 |
| R-02 | 企业全景结论 | 页面展示整体风险等级、简明摘要、关键正面与负面信号 | 每个确定性结论至少关联一个可访问来源或明确标注为派生指标；LLM 摘要必须显示引用证据 |
| R-03 | 财务健康分析 | 展示收入、利润、经营现金流、资产负债率等趋势及解释 | 至少展示连续多个报告期；指标必须标明报告期、单位和来源 |
| R-04 | 偿债与信用风险 | 展示短期偿债压力、负债、诉讼/执行/处罚等可获得风险信号 | 不存在数据时显示「未检索到」或「数据不可用」，不得表述为「不存在风险」 |
| R-05 | 经营与舆情事件 | 按时间展示公告、新闻或风险事件，并标记事件类型和影响方向 | 每条事件包含日期、摘要、来源名称与原始链接 |
| R-06 | 证据追溯 | 用户可从风险项或指标打开其来源信息 | 重要结论可追溯到原始链接、数据字段或计算公式 |
| R-07 | 数据状态 | 页面展示数据覆盖范围、来源与本次查询时间 | 当数据缺失、采集失败或查询仍在进行时，有可理解的状态与降级提示 |
| R-08 | 多源信息处理 | 系统可接入官方 API、公开网页、合规开放数据或社交平台信息 | 每条来源记录都标记来源类型、适配器、获取时间与可信度等级；社交内容不能单独作为财务或信用事实 |
| R-09 | LLM 叙述 | 系统将已验证的指标、事件与证据转为简明中文解释 | LLM 输出只可引用输入证据 ID；调用失败时保留规则生成的基础结论，不阻断报告 |

### 3.5 体验要求

- 界面与企业信息仅使用简体中文。
- 首屏在一次查看中回答「这家公司怎样、最大风险是什么、依据是什么」。
- 使用颜色、图标和文字共同表达风险等级，不能仅依赖红绿配色。
- 图表服务于趋势和比较；每张图都应有清晰标题、时间范围、单位和数据来源。
- 图表使用一致的视觉语言和可扫描的信息层级；浏览器组件可根据报告中的图表语义渲染折线、柱状、面积、雷达和时间线等图形，但颜色、布局和交互由前端统一控制。
- 重要图表应支持查看指标定义、原始数值、时间范围和关联证据，不能只输出装饰性图形。
- 风险结论应使用审慎措辞，例如「存在压力信号」「建议进一步核验」，避免将公开信息推断为确定事实。
- 所有由规则或模型生成的摘要都要与证据链接相邻展示。

## 4. 分模块需求边界

| 模块 | 负责内容 | 本期不负责 |
|---|---|---|
| 数据获取 | 在单个 Node.js Worker 中查询企业身份；通过可插拔适配器获取官方 API、公开网页、合规开放数据和社交线索；统一字段、保存来源、采集时间、可信度与失败原因；维护 SQLite 作业生命周期 | 业务评分、投资/授信结论、浏览器展示逻辑；绕过登录、反爬或平台规则 |
| 数据分析 | 消费标准化快照，计算指标与趋势；运行确定性风险规则；构造受证据约束的 LLM 叙述输入；生成整体风险等级、维度结论与可解释摘要 | 直接爬取数据、替代人工尽调、让 LLM 单独生成事实或风险等级 |
| 结果呈现 | 在 Next.js 浏览器组件中支持查询、展示总览/图表/事件时间线/证据；表达空态和异常态；按图表语义统一视觉与交互 | 修改原始数据、重新定义指标口径、隐去来源、把图表样式决策泄漏到分析模块 |

## 5. 风险分级与解释原则

本期的风险等级是面向演示和初步筛查的解释性结果，不构成授信、投资、存款或其他金融决策建议。

每个维度都应同时展示：

- **信号：** 例如经营现金流持续下降、资产负债率上升、重大诉讼事件。
- **判断依据：** 原始数据、时间范围和阈值或计算方式。
- **影响说明：** 该信号可能说明什么，以及为什么需要关注。
- **数据局限：** 缺少报告期、来源不可访问、事件尚未核验等情况。

整体等级确定为低、中、高三个层级。首版采用可解释规则汇总：每条风险信号必须有来源和依据；严重单项风险或多个中度风险可以提升整体等级；数据不足不降低风险等级。具体指标阈值、权重和汇总规则由数据分析模块在实现前登记，可在不改变接口语义的前提下继续调整。

## 6. 本期明确不做

- 不做自动授信审批、投资建议、企业信用认证或任何替代人工决策的功能。
- 不承诺覆盖所有企业、所有公开网站或实时全网信息。
- 不使用未经授权的付费数据、个人隐私数据或需要登录绕过的内容；不绕过网站反爬限制或平台访问规则。
- 不在本期训练专有金融大模型，或承诺预测企业未来股价、违约概率；LLM 不作为事实、财务数值或风险等级的唯一来源。
- 不做多用户账号、权限体系、长期历史存储、移动端 App 与生产级部署。
- 不把「未获取到风险信息」显示成「企业没有风险」。

## 7. 演示验收场景

### 场景 A：查看风险信号明显的示例企业

1. 输入已准备的公司名称或股票代码。
2. 在总览页看到整体风险等级和至少三项关键线索。
3. 打开一项财务或风险线索，看到数据、时间范围、来源与解释。
4. 在事件时间线中看到其对应的公告、新闻或公开事件。

**通过条件：** 链路可在现场网络或预置数据条件下稳定完成；结论不依赖无法解释的黑箱分数。

### 场景 B：查询数据不足的企业

1. 输入系统不支持或公开数据不足的企业。
2. 系统说明无法完成哪些维度、已检索到哪些信息。

**通过条件：** 无虚构指标、无空白崩溃、无把数据缺失误判为低风险。

## 8. 待确认项

以下事项影响后续技术框架、数据源选择和接口契约，须由团队确认：

1. **演示企业：** 选择哪些企业作为主演示对象，是否需要一正一负两组对照。
2. **数据源优先级：** 各数据维度应优先使用哪个公开来源，以及当该来源失败时是否允许回退至其他公开来源。
3. **风险口径细节：** 三档风险的具体指标阈值、行业差异和最终汇总规则；首版允许在数据分析实现前继续调整。

## 9. 成功标准

本项目成功不以采集数据量衡量，而以评委能否在几分钟内清楚理解以下因果链衡量：

```text
多种公开来源与原始证据
  → 可替换适配器与统一溯源记录
  → 标准化企业数据与确定性财务/信用/风险信号
  → 受证据约束的 LLM 叙述与图表语义
  → 面向决策者的企业全景结论
```
