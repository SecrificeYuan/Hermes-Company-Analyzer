# 开发计划

## 目标

在比赛剩余时间内交付一个可在线查询 A 股上市公司的 Web 原型。它应从真实公开信息形成可追溯的企业风险画像，而非仅展示静态样例或黑箱评分。

## 今晚：协作地基

| 交付物 | 完成条件 |
|---|---|
| 需求与范围 | 已确认用户、范围、验收场景与本期不做项 |
| 架构与技术框架 | 明确三模块边界、数据流、状态归属和技术选择 |
| 接口契约 | 冻结任务 API、企业快照和分析报告的 v1 形状与失败语义 |
| Git 协作骨架 | 已初始化仓库，包含协作规则、忽略规则、目录和决策记录机制 |

## 明天：三模块并行开发

| 模块 | 负责人任务 | 依赖 | 对外完成标志 |
|---|---|---|---|
| 数据获取成员 | 只负责 `apps/worker/src/acquisition/` 与 `orchestration/`；完成公司候选解析、一个官方来源适配器、标准化快照、SQLite 作业领取和 Worker 轮询 | 适配器契约、快照模型、SQLite 作业字段 | 对目标 A 股企业能产出带来源、可信度和状态的快照；单一来源失败不阻断其他来源 |
| 数据分析成员 | 只负责 `apps/worker/src/analysis/`；完成快照校验、指标趋势计算、确定性风险规则、Evidence Pack、LLM 回退模板和报告生成 | `CompanySnapshot v1`、LLM 契约 | 每个结论均有证据或明确的数据不足原因；LLM 失败时仍产出基础报告 |
| 结果展示成员 | 只负责 `apps/web/`；完成 Next.js 查询与轮询、总览、ECharts 图表、时间线、证据视图和 Route Handlers | HTTP API、`AnalysisReport v1` 与图表模型 | 可处理 queued、fetching、normalizing、analyzing、generating_narrative、succeeded、partial、failed 状态 |

## 集成顺序

1. 三人先以 `contracts/fixtures/` 中的契约样例并行开发，不等待彼此的业务实现。
2. 数据获取完成第一份真实快照后，数据分析只替换其输入；不改快照字段。
3. 数据分析完成第一份真实报告后，结果呈现只替换 API 地址；不改页面所消费的报告字段。
4. 端到端联调只允许在 v1 契约下修复实现问题。需要改字段、枚举或失败语义时，暂停联调并按契约变更流程处理。

## 集成关卡与验收

| 关卡 | 通过条件 | 不通过时的处理 |
|---|---|---|
| G1 契约冻结 | 三位负责人认可 `contracts/` 的字段、状态和所有权 | 记录问题，先修改契约再开始模块实现 |
| G2 真实数据快照 | 给定 A 股名称可在线获得至少核心财务和来源信息；其他维度可显式部分成功；不同来源保留统一溯源元数据 | 数据获取模块修复适配器或标记维度不可用 |
| G3 分析报告 | 对快照生成可验证的信号、总览、证据引用和可选 LLM 叙述 | 数据分析模块补规则或修复映射；LLM 不可用时回退基础结论 |
| G4 UI 串联 | 浏览器完成查询、轮询、总览、图表、下钻、空态与失败态；图表可查看数据来源 | 由接口调用方记录可复现请求，责任模块修复 |
| G5 演示验收 | 按需求文档的场景 A/B 走通，所有重要结论可追溯 | 降级非核心维度，不牺牲证据和状态表达 |

## 分支与合并约定

- 主分支使用 `main`，保持可运行或至少可通过已有检查。
- 每个成员从 `main` 创建自己的功能分支，建议命名 `feat/acquisition-*`、`feat/analysis-*`、`feat/presentation-*`。
- 任何人不得在未沟通的情况下改他人正在负责的目录；共享的 `contracts/` 和 `docs/` 由改动发起人先在群内说明。
- 合并前至少执行所在模块的验证；首次联调前对照契约样例检查字段和状态。

## 明确延后

- 具体数据源适配实现与单站点字段映射。
- 指标阈值、行业比较和风险权重的细节。
- 图表主题、页面视觉细节和具体 LLM 提示词。
- SQLite 的具体表实现、性能优化与生产部署。

这些内容明天以各模块任务卡落实，不应阻塞今晚的协作契约建立。
