# Agent Note: 初始协作架构与契约

- Status: implemented
- Date: 2026-10-02
- Class: architecture

## Problem

48 小时 Hackathon 由三人分别实现数据获取、数据分析和结果呈现。题目要求用户输入任意给定的 A 股企业后，网站在线使用真实公开信息给出可追溯的分析。若先各自编码，采集结果、分析口径和前端状态很容易在联调时不兼容。

## Decision

将首版限定为 A 股上市公司和中文界面。采用 React + TypeScript Web 前端与 Python + FastAPI 单体 API 的结构；查询通过异步 `AnalysisJob` 执行。数据获取输出 `CompanySnapshot v1`，数据分析输出 `AnalysisReport v1`，前端只通过 OpenAPI 读取任务和报告。

风险使用低、中、高和 `unknown` 四个状态。每一条结论必须引用证据；数据缺失与来源失败被表达为 `partial` 或 `unavailable`，不降级为低风险。今晚冻结 v1 的字段和失败语义，明天的三个模块以契约夹具并行开发。

## Alternatives considered

1. 前端直接调用多个公开数据源：放弃，因为跨域、数据源失败和来源追溯逻辑会分散到页面，且无法复用统一分析结果。
2. 将采集、分析和展示拆成三个独立服务：放弃，因为 48 小时内会增加部署、认证和调试成本，模块边界可先由单体 API 内的契约保证。
3. 同步返回一次查询的完整结果：放弃，因为真实在线数据获取耗时和失败不可预测，前端无法正确表达加载、局部失败和重试状态。
4. 直接用一个 0-100 的黑箱总分：放弃，因为题目强调「透视·真相」，评委和用户需要理解证据与不确定性。

## Consequences

数据源适配、指标阈值和 UI 视觉细节可以在不改变 v1 契约的情况下独立推进。若实际开发发现需要改枚举、字段含义或任务状态，必须先按 `contracts/README.md` 的变更流程讨论，不能为了局部实现静默修改。
